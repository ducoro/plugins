# Customer Support Ops Data Schema

This directory layout works inside the human's existing support folder, a single Space's `files/` directory, or an optional cross-Space Local Folder. Pass the chosen path explicitly as `<data-dir>` to every bundled script. Boards are never stored inside `<data-dir>`; project them into the displaying Space's own `boards/<board-id>/`.

```text
<data-dir>/
├── sla-policy.json            # SLA hours (P0-P3), replyCooldownHours, spike thresholds, routine approval flag
├── tickets/
│   └── tickets.json           # Deduplicated ticket store keyed by ticketId (channel:externalId)
├── issues/
│   └── root-causes.json       # Root-cause cluster catalog keyed by rootCauseId
├── outbound-queue.json        # Staged & approved reply drafts with sha256 approval hash
├── reply-log.jsonl            # Append-only sent reply audit ledger (source of truth for replied status & cooldown)
├── sla-report.json            # Latest deterministic output from triage_gate.py (includes full clusterMetrics)
└── kb/                        # Verified support macros & troubleshooting articles
```

## SLA Policy Schema (`sla-policy.json`)

If `sla-policy.json` is absent, `triage_gate.py` and `reply_guard.py` fall back to these exact defaults:

- `schemaVersion`: `"customer-support-sla/1"`
- `firstResponseHours`: `{ "P0": 1, "P1": 4, "P2": 24, "P3": 72 }`
- `replyCooldownHours`: `24` (hours within which unapproved new follow-ups without a newer inbound customer message are blocked)
- `spikeMinRecentCount`: `3` (minimum tickets in the recent 7-day window to trigger a spike)
- `spikeMinUniqueCustomers`: `2` (anti-false-consensus minimum distinct customers in the recent 7-day window)
- `spikeRatioThreshold`: `2.0` (minimum `recent7dCount / prior7dCount` ratio when `prior7dCount > 0`)
- `requireApprovalForRoutine`: `false` (when `true`, even routine P2/P3 replies stage as `awaiting_approval`)

## Ticket Schema (`customer-support-ticket/1`)

- `ticketId`: deterministic ID (`<channel>:<externalId>`)
- `channel`: e.g., `"github_issues"` | `"appstore_ios"` | `"email"` | `"discord"` | `"slack"` | `"csv"` | `"connector"` | `"computer_use"` | `"web"`
- `externalId`: upstream ticket/issue/review/message ID
- `customer`: sender/author identifier
- `subject`: short title
- `body`: raw feedback text
- `url`: optional source URL (`http(s)://`)
- `rating`: optional integer `1`–`5` (for app store reviews or CSAT exports)
- `vip`: optional boolean (`true` elevates to at least `P1` and flags `vip_customer`)
- `labels`: optional array of strings (e.g., `["security"]`, `["billing"]`, `["bug"]`)
- `riskFlags`: optional array of explicit model/human risk codes (e.g., `"p0_outage"`, `"security_privacy"`, `"legal_regulatory"`, `"billing_refund"`, `"churn_signal"`)
- `createdAt`: ISO-8601 UTC timestamp
- `lastInboundAt`: optional ISO-8601 UTC timestamp of the customer's latest inbound follow-up (unlocks reply cooldown when newer than `reply-log.jsonl`'s latest `sentAt`)
- `status`: `"open"` | `"pending_human"` | `"replied"` | `"resolved"` (effective replied state is derived from `reply-log.jsonl` without `reply_guard.py` mutating `tickets.json`)
- `rootCauseId`: optional root-cause cluster slug
- **Triage-computed fields (monotonic—never downgraded on re-run)**: `priority` (`P0`–`P3`), `escalationReasons` (merged array), `heuristicSignals` (keyword safety-net hints), `requiresHumanApproval`, `autoReplyAllowed`, `effectiveStatus`, `ageHours`, `slaLimitHours`, `slaBreached`

## Root-Cause Catalog Schema (`issues/root-causes.json`)

```json
{
  "schemaVersion": "customer-support-root-causes/1",
  "updatedAt": "2026-11-27T00:00:00Z",
  "clusters": {
    "macos-sync-hang": {
      "title": "macOS startup sync hangs at 0%",
      "area": "sync",
      "vocTier": "blocker_bug",
      "status": "investigating",
      "notes": "Linked to 3 distinct customers after v2.4 update"
    }
  }
}
```

## Triage Report Schema (`sla-report.json`)

Generated by `scripts/triage_gate.py <data-dir> --write-report`:

- `openCountsByPriority`: open counts by `P0`–`P3` (after deriving replied status from `reply-log.jsonl`)
- `escalations`, `slaBreaches`, `spikes`, `kbDeflectionCandidates`
- `clusterMetrics`: complete map keyed by `rootCauseId` with real `totalTickets`, `uniqueCustomers`, `recent7dUniqueCustomers`, `totalUniqueCustomers`, `recent7dCount`, `prior7dCount`, `spikeRatio`, and `isSpiking` for both spiking and steady clusters
